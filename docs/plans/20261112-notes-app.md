# Notes App — Self-Hosted Notes with Nested Folders and Secure Sharing

## Overview
- A secure, self-hostable web Notes app: nested folders, TipTap rich-text editing, and zero-public-access sharing (PIN-gated link or HMAC-signed expiring link).
- Runs as a single Docker container (Fastify serves API + built SPA) with all state in one `/data` volume (SQLite + uploads), so export/backup is copying files.
- Greenfield project at `~/tools/notes-app` (new git repo). Multi-user collaboration is deferred; only an access-resolution seam is built now.

## Context (from discovery)
- Greenfield: no existing code. `~/tools/notes-app` was created and `git init`-ed during planning.
- **Node/npm are NOT on PATH on the dev machine** (`node: command not found`) — Task 1 installs/verifies Node 22 first.
- Stack: monorepo `apps/web` (React + Vite + Tailwind + shadcn/ui + TipTap + TanStack Query + @dnd-kit + react-resizable-panels) and `apps/server` (Fastify + TypeScript + better-sqlite3 + zod).
- Authorization replaces Postgres RLS: an owner-scoped repository layer (every query requires `userId`, except the clearly marked `repos/publicShare.ts` used by the public shared API and the attachment sweep); other users' resources return 404, never 403.

## Solution Overview
- **Single container, single origin**: Fastify serves `/api/*` and the built SPA — no CORS. Config via env: `SESSION_SECRET`, `SHARE_HMAC_KEY` (server refuses to boot if missing/short), `PUBLIC_ORIGIN` (required, e.g. `https://notes.example.com`), `TRUST_PROXY` (number of trusted proxy hops, or a comma-separated list of trusted proxy IPs/CIDRs; default unset = trust nothing; never a bare `true`), `ALLOW_SIGNUP` (default true), `DATA_DIR`, `HOST` (default `0.0.0.0`), `PORT`.
- **Auth**: email + password (argon2id), server-side sessions in SQLite. Cookie is `HttpOnly; SameSite=Lax`, plus `Secure` whenever `PUBLIC_ORIGIN` is https. CSRF: SameSite + exact match of the `Origin` header against `PUBLIC_ORIGIN` on every mutating request; a mutating request with no `Origin` is rejected. Login is rate-limited per (account, IP key) pair and per IP key, plus an atomic per-account delay gate that browsers which have logged in before (device cookie) bypass, so nobody can lock the owner out of a known device remotely; signup is rate-limited per IP key; successful logins and change-password are rate-limited too; all argon2 work goes through a global concurrency cap with one slot reserved for the **owner account** (first account created) on a known device. One password policy (min 10 chars, max 256) enforced by a single `validatePassword` used by signup, change-password and the reset CLI. Password management: CLI `npm run reset-password -- <email>` and in-app change-password. No email reset.
- **Authorization**: repo layer requires `userId` on every query; `resolveAccess(userId, noteId)` returns `owner | none` (seam for future multi-user). Ownership applies to every id the caller supplies — path params **and** body fields (`parent_folder_id`, `folder_id`, move targets): a foreign or missing id → 404. The single exception is `repos/publicShare.ts`, the only module allowed to query without a `userId` (used by the public shared API and the attachment sweep); it is read-only apart from the sweep's deletes, and each function documents why it is unscoped.
- **Content** stored as TipTap JSON. Images in content reference attachments by id (`attachment://<aid>` in the stored JSON). A custom TipTap image extension resolves that to a real URL **only inside a ProseMirror node view** (owner editor: owner attachment URL; shared view: blob URL). Its `renderHTML` (used for the clipboard) and `parseHTML` keep the reference as `src="attachment://<aid>"` plus `data-attachment-id`, so copy, cut and paste — within a note or across notes — always keep `attachment://<aid>`, and stored content never contains a private route.
- **Attachments belong to the user, not to a note.** A `note_attachments(note_id, attachment_id)` reference table is rebuilt from the content on every content save, so an image pasted into several notes is referenced by each of them. Deleting a note only removes its references. Images are deleted only by the sweep, after nothing has referenced them for 7 days.
- **Concurrency**: notes carry an integer `version` that guards **content only**. Autosave sends `{content, version}`; each successful content save increments and returns `version`; a stale `version` → 409. Title changes (from the editor title field or the sidebar) and moves go through separate metadata endpoints that neither send nor change `version`, so a rename can never be reverted by an autosave.
- **Sharing**: two modes on `notes.share_type`. Password: 8-char PIN, argon2-hashed in `share_secret`, shown once, unlock yields a 30-min HMAC token. Signed URL: `sig = HMAC-SHA256(SHARE_HMAC_KEY, note_id|exp|nonce)`, nonce in `share_secret`, rotated on regenerate/stop to revoke. Public shared API is a separate surface that never reads the session cookie.
- **Tree**: one flat `GET /api/tree` (no content); client builds the nested tree; optimistic updates with rollback. Folder cycles blocked in UI and authoritatively on the server (recursive CTE → 409).

## Technical Details
- **Schema**: `users(id uuid, email UNIQUE, password_hash, is_owner INTEGER NOT NULL DEFAULT 0, created_at)` with a partial unique index `ON users(is_owner) WHERE is_owner = 1` (at most one owner; the first account created by signup gets `is_owner = 1`, decided inside the same transaction that checks the table is empty, so two simultaneous first signups cannot both become owner), `sessions`, `folders(id uuid, user_id, name, parent_folder_id nullable ON DELETE CASCADE, created_at)`, `notes(id uuid, user_id, folder_id nullable ON DELETE CASCADE, title, content JSON, version INTEGER NOT NULL DEFAULT 1, created_at, updated_at, share_type CHECK IN ('private','password_protected','signed_url'), share_secret, expires_at)`, `known_devices(id uuid, user_id FK ON DELETE CASCADE, token_hash UNIQUE, created_at, last_used_at)`, `attachments(id uuid, user_id FK, original_name, storage_name UNIQUE, mime, size, created_at INTEGER unix seconds, last_unlinked_at INTEGER unix seconds nullable)` (no `note_id`), `note_attachments(note_id FK ON DELETE CASCADE, attachment_id FK ON DELETE CASCADE, PRIMARY KEY(note_id, attachment_id))`, plus trigger `note_attachments_unlinked AFTER DELETE ON note_attachments FOR EACH ROW BEGIN UPDATE attachments SET last_unlinked_at = unixepoch() WHERE id = OLD.attachment_id; END`. The trigger fires for explicit deletes **and** for FK cascade deletes (a deleted note, or a folder deleted at any depth above it), so the moment an image loses a reference is always recorded without any application code. All ids are UUIDv4 generated server-side (never autoincrement). `storage_name` is the random on-disk file name; `original_name` is display-only and never used in a path. Migrations are numbered plain `.sql` files run at boot; SQLite in WAL mode with `foreign_keys=ON`.
- **Server layout**: `routes/`, `services/` (share, tree, attachments), `repos/`, `db/`.
- **Web layout**: `features/{auth,tree,editor,share}`.
- **PIN unlock rate limit**: keyed on the requested note id **whether or not the note exists or is PIN-shared**, 5 failures / 15 min → 429 lockout; plus a per-IP-key limit (30 unlock attempts / 15 min, same normalized IP key as login). The lockout check runs **before** any argon2 verify, so a locked id returns 429 even for the correct PIN and costs no hashing. Because the counter is id-agnostic, the 429 reveals nothing about whether a share exists; apart from 429, every failure is the identical "unavailable" response.
- **Login rate limit**, checked in this order, all **before** any argon2 work:
  1. **Per IP key**: 30 failures / 15 min → 429.
  2. **Per (account, IP key)**: 10 failures / 15 min → 429.
  3. **Per-account delay gate** (skipped when the request carries a valid device cookie for that account): state per account is `{failures, nextAllowedAt}`, keyed by the normalized email string so unknown emails behave identically. If `now < nextAllowedAt` → 429 with `Retry-After`, immediately (rejected, never queued or slept). Otherwise, **synchronously, before the first `await`**, set `nextAllowedAt = now + delay` where `delay = failures < 5 ? 0 : min(2^(failures−5) × 250 ms, 5 s)`, then verify. Failure → `failures++`; success → reset. Because Node runs the check-and-set without yielding, at most one attempt per account gets through per window no matter how many arrive in parallel, which caps guessing at ~17k/day per account from any number of IPs.
  - **Device cookie**: on successful login, issue a long-lived (1 year) `HttpOnly; Secure-when-https; SameSite=Lax` cookie containing a random id, stored hashed in `known_devices(id, user_id, created_at, last_used_at)`. A login attempt with a valid device cookie **for the same account** skips only the delay gate (still subject to 1 and 2). So an attacker saturating the gate cannot keep the owner out of a browser they have used before; a brand-new device under attack may have to wait for a free window, which the README states. Change-password and the reset CLI delete that user's `known_devices` rows.
  - Unknown emails run a dummy argon2 verify for uniform timing, under the same limits. The limiter state is in memory (single process); a restart clears it.
- **Client IP key**: all per-IP limits use Fastify `request.ip`, normalized: an IPv4-mapped IPv6 address (`::ffff:a.b.c.d`) is first unwrapped to plain IPv4; then IPv4 keys on the full address and native IPv6 on its /64 prefix (one VPS's /64 counts as one client). The server listens on `HOST` (default `0.0.0.0`) so the normalization is exercised whichever stack Node uses. `request.ip` is only correct when `TRUST_PROXY` matches the deployment, and whenever `TRUST_PROXY` is set the app port must not be reachable except through that proxy (otherwise a direct request can forge `X-Forwarded-For`). README gives the exact setup for each deployment (Task 19). With no proxy, leave it unset.
- **argon2 concurrency cap**: a semaphore of 5 slots. 4 general slots serve every hash (signup, login, unknown-email dummy verify, PIN unlock, reset/change password); excess requests wait briefly, then get 503. **1 reserved slot** may be used only by the **owner account** (`is_owner = 1`): a login for the owner's email carrying a valid owner device cookie, or a change-password from an owner session. No other account can ever acquire it, so neither anonymous hashing nor floods from self-registered accounts can 503 the owner on a known device.
- **Signup rate limit**: 5 signups / hour per IP key → 429, checked before any argon2 work.
- **Successful-login and change-password limits** (so no account can generate unbounded argon2 work or rows): successful logins 20 / 15 min per account and 20 / 15 min per IP key → 429; change-password 5 / 15 min per user → 429. All checked before any argon2 work. Each successful login reuses the presented device cookie's `known_devices` row instead of creating a new one. `ALLOW_SIGNUP` still defaults to true (README recommends `false` once the owner account exists on a public deployment).
- **Attachments**: 10 MB limit; PNG/JPEG/WebP/GIF only (no SVG), checked by magic bytes; stored as `DATA_DIR/uploads/<storage_name>`. Owner routes: `POST /api/attachments` (upload; returns `{id}`), `GET /api/attachments/:aid` (owner-scoped).
  - **Upload** writes the file, then inserts the row (`last_unlinked_at` NULL).
  - **Content save** (one transaction): extract every `attachment://<aid>` from the content, keep only ids that belong to the **same user** (foreign or unknown ids are ignored, so a user can't link someone else's image into their share), and make that note's `note_attachments` rows equal that set (delete removed ids, insert new ones). Deleted rows fire the trigger, which stamps `last_unlinked_at` with the time the reference was removed.
  - **Note or folder delete**: nothing attachment-specific. The FK cascade removes the deleted notes' `note_attachments` rows (through any depth of nested folders), and the trigger stamps `last_unlinked_at` for each.
  - **Sweep** (at boot and daily; takes `now` as a parameter so tests can advance time): deletes attachments that have **no `note_attachments` rows** and whose `MAX(created_at, COALESCE(last_unlinked_at, 0))` is older than `now − 7 days` (row first, file after commit). The grace is therefore always counted from the moment the image lost its last reference (or from upload, if it was never referenced), which covers cut/paste, undo, deleted notes, nested-folder deletes and never-saved uploads. Stray files with no row are deleted **only if older than 1 hour** (so an upload still writing its file or about to insert its row is never touched).
  - **Shared access**: `/api/shared/:id/attachments/:aid` serves an attachment only if a `note_attachments` row links it to note `:id`.
- **Shared view**: payload is only title, content and the attachment ids linked to the note in `note_attachments`; read-only TipTap (`editable:false`). Image nodes are resolved by the shared view and loaded with `fetch` (PIN mode: token in an `Authorization` header; signed mode: the page's own `exp`/`sig` as query params) and rendered as blob URLs — the unlock token never goes into a URL. `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex` on **both** `/api/shared/*` responses and the `/shared/*` HTML page. Wrong PIN / expired / revoked / missing → identical generic "unavailable".
- **Expiry options**: 1h / 1d / 7d / 30d (max 30d). PIN shares have no expiry.
